# 다중 전문의 AI 문진 앱 — 설계 문서

- 작성일: 2026-08-28
- 상태: 승인됨 (구현 계획 진행 중)
- 용도: 개인/학습용 프로토타입 (실제 의료 진단 대체 아님)

## 1. 목적

전화 녹음(통화 녹음) 파일을 업로드하면:

1. 녹음 내용을 텍스트로 전사한다.
2. 전사 내용과 관련된 전문 분야(내과, 호흡기내과, 이비인후과, 정신건강의학과 등)를 동적으로 선택해 전문의 에이전트를 소집한다.
3. 각 전문의 에이전트가 1차 의심 질환과 확인이 필요한 추가 질문을 제시한다.
4. 여러 전문의의 질문을 하나로 통합한 문진(인터뷰) 화면에서 사용자에게 순차적으로 묻는다. 사용자는 텍스트, 음성, 파일(사진 등) 중 원하는 방식으로 답변할 수 있다.
5. 문진 답변을 반영해 각 전문의가 최종 소견(의심 질환 + 확신도)을 확정한다.
6. 별도의 종합 에이전트가 모든 전문의 소견을 취합해 종합의견을 제시한다.

이 앱은 개인/학습용 프로토타입이며 실제 의료 진단을 대체하지 않는다. 모든 화면에 면책 문구를 고정 표시한다.

## 2. 범위 결정 사항 (브레인스토밍에서 확정)

- **용도**: 개인/학습용 프로토타입 — 과도한 컴플라이언스 장치 없이 빠르게 구현, "진단 보조 참고 정보"로 명확히 고지.
- **기술 스택**: Next.js (App Router) + Vercel AI SDK, Vercel AI Gateway를 통한 모델 호출.
- **전문의 에이전트 구성**: 고정된 전체 목록이 아니라, 녹음 내용을 트리아지 에이전트가 먼저 읽고 관련된 2~4개 전문 분야를 동적으로 선택하여 해당 에이전트만 호출한다.
- **문진 입력 방식**: 텍스트, 음성(STT 처리), 파일 첨부(사진 등) 모두 지원한다.
- **세션/데이터 저장**: 단일 세션, 서버 측 영구 저장 없음. 새로고침 시 기록 소실. 로그인/회원가입 없음. 민감한 의료 데이터 보관 부담을 최소화하기 위한 결정.
- **전체 파이프라인 구조**: 통합 문진 + 별도 종합 에이전트. 전문의 에이전트들이 제안한 질문을 하나의 대화 흐름으로 병합하여 사용자가 중복 질문을 받지 않도록 한다. 종합 소견은 전문의 소견을 취합하는 별도 에이전트가 작성한다.

## 3. 아키텍처

```
[사용자] --녹음파일 업로드(mp3/wav/m4a)--> [Next.js 앱]
              |
              v
     [1단계: 전사(Transcription)]
     Vercel AI Gateway STT 모델(예: gpt-4o-transcribe) 사용, 한국어 지원
              |
              v
     [2단계: 트리아지 에이전트]
     전사 텍스트를 읽고 관련 전문분야 2~4개 동적 선택
     (예: "가슴이 답답하고 기침을 오래 했다" → 호흡기내과, 심장내과)
              |
              v
     [3단계: 전문의 에이전트 N개] (병렬 초기 분석)
     각자 전사문 기반으로 1차 의심 질환 + 확인이 필요한 질문 목록 제안
              |
              v
     [4단계: 통합 문진 UI] (멀티턴 채팅형)
     여러 전문의의 질문을 하나의 대화 흐름으로 순차 제시(질문마다 "어느 전문의가 묻는지" 표시)
     사용자 답변: 텍스트 입력 / 음성 녹음(STT 처리) / 파일첨부(사진 등) 모두 지원
              |
              v
     [5단계: 전문의별 최종 소견]
     각 전문의 에이전트가 문진 답변을 반영해 의심 질환 및 확신도 갱신
              |
              v
     [6단계: 종합 에이전트]
     모든 전문의 소견을 취합해 종합의견(가능성 높은 진단, 권장 조치, 주의사항) 생성
              |
              v
     [결과 화면] 전문의별 카드 + 종합소견 카드
```

## 4. 컴포넌트 구성 (Next.js App Router 기준)

- `app/page.tsx` — 업로드 & 결과 표시 메인 화면
- `app/api/transcribe/route.ts` — 오디오 업로드 → STT 처리
- `app/api/triage/route.ts` — 전사문 기반 관련 전문분야 선택
- `app/api/specialists/route.ts` — 선택된 전문의 에이전트 병렬 초기 분석 (Vercel AI SDK `generateObject`로 구조화된 출력)
- `app/api/interview/route.ts` — 문진 답변 처리(텍스트/음성/파일), 다음 질문 생성, 답변을 해당 전문의 컨텍스트에 반영
- `app/api/synthesize/route.ts` — 종합 에이전트 호출
- `components/UploadPanel.tsx` — 녹음 파일 업로드
- `components/InterviewChat.tsx` — 멀티모달 입력(텍스트박스 / 마이크 버튼 / 파일첨부)을 지원하는 통합 문진 채팅 UI
- `components/SpecialistCard.tsx` — 전문의별 소견 카드
- `components/SynthesisReport.tsx` — 종합의견 카드
- `lib/agents/` — 전문의 페르소나 프롬프트 정의(과별로 분리된 시스템 프롬프트 파일)
- 상태 관리는 클라이언트 React state만 사용 — 서버 DB 없음

## 5. 에이전트 프로토콜 (데이터 스키마)

전문의 에이전트 공통 응답 스키마:

```ts
type SpecialistOpinion = {
  specialty: string; // 예: "호흡기내과"
  suspectedConditions: {
    name: string;
    confidence: number; // 0~1
    rationale: string;
  }[];
  followUpQuestions: {
    question: string;
    reason: string;
  }[];
};
```

종합 에이전트 응답 스키마:

```ts
type SynthesisReport = {
  overallImpression: string;
  topDifferentials: {
    condition: string;
    supportingSpecialties: string[];
    confidence: number;
  }[];
  recommendedActions: string[];
  redFlags: string[]; // 응급 신호 감지 시 채움
};
```

흐름:

1. 통합 문진 UI는 모든 전문의의 `followUpQuestions`를 하나의 큐로 병합한다. 트리아지 단계에서 유사/중복 질문을 병합하는 로직을 둔다.
2. 답변이 들어올 때마다 해당 질문을 낸 전문의 에이전트만 재호출한다(전체 재분석 아님 — 비용/속도 최적화).
3. 모든 문진이 끝나면 각 전문의 에이전트가 최종 소견을 확정하고, 종합 에이전트가 이를 취합한다.

## 6. 의료 면책 및 안전장치

- 모든 화면 상단/하단에 "이 앱은 실제 의료 진단을 대체하지 않으며 학습·참고 목적입니다. 응급 증상 시 119 또는 응급실 방문" 고정 배너 표시.
- 응급 키워드(가슴통증+호흡곤란, 의식소실, 심한 출혈 등) 감지 시 별도 강조 경고 표시.
- 업로드된 오디오/전사문/문진 답변은 서버에 영구 저장하지 않고 세션(메모리) 범위에서만 유지한다. 새로고침 시 소실된다.

## 7. 테스트 전략

- 에이전트 프롬프트/스키마 검증: 샘플 전사문 3~5개로 각 에이전트 출력이 스키마를 따르는지 유닛 테스트.
- API route 통합 테스트: 전사 → 트리아지 → 전문의 → 문진 → 종합 전체 흐름을 mock 모델 응답으로 1회 실행.
- 브라우저에서 실제 오디오 파일 업로드 후 전체 플로우 수동 검증(음성 답변 녹음 포함).

## 8. 범위 밖 (Out of scope, 이번 프로토타입에서 다루지 않음)

- 사용자 계정/로그인, 과거 기록 조회.
- 실제 의료기관 연동, 처방/예약 기능.
- 다국어 지원(한국어만 지원).
- HIPAA/개인정보보호법 수준의 컴플라이언스 장치(암호화 저장, 감사로그 등) — 개인/학습용 프로토타입이므로 저장 자체를 하지 않는 방식으로 리스크를 회피.
