# 진입 화면 재구성 및 기본정보(연령대/성별/직업) 수집 — 설계 문서

- 작성일: 2026-09-12
- 상태: 승인됨 (구현 계획 작성 예정)
- 용도: 개인/학습용 프로토타입의 확장 — 실제 의료 진단을 대체하지 않는다는 원칙은 유지

## 0. 이 문서가 바꾸는 것

`docs/superpowers/specs/2026-09-11-accounts-medical-records-design.md`와 `CLAUDE.md`의 핵심 전역
제약 중 다음 항목을 이 문서가 대체한다.

> 게스트 로그인은 기존과 동일하게 아무것도 저장하지 않는다.

무계정 게스트 모드를 **완전히 제거**한다. 이제 앱을 사용하려면 반드시 로그인(손님입장) 또는
회원가입을 거쳐야 한다. 로그인/회원가입 방식(이메일 + 비밀번호, Clerk)과 회원의 문진 결과 영구
저장 로직 자체는 2026-09-11 문서에서 바뀌지 않는다 — 이 문서는 "게스트로 계속하기" 진입 경로 하나만
없앤다.

또한 회원가입 직후 수집하는 프로필 정보를 전화번호 하나에서 **전화번호 + 연령대 + 성별 + 직업**
네 가지로 확장하고, 이 정보를 문진 결과 저장뿐 아니라 **트리아지·전문의 1차 분석 AI 프롬프트에도
전달**한다. 앱 이름을 "다중 전문의 AI 문진"에서 "홈 닥터"로 바꾼다.

기존 7단계 문진 파이프라인의 핵심 로직(전사 → 트리아지 → 전문분야 선택 → 전문의 병렬 분석 → 문진
병합 → 통합 문진 루프 → 종합)은 바뀌지 않는다. 이 스펙은 진입 전 단계(온보딩)와 AI 프롬프트에
넘어가는 입력값 하나를 넓히는 것이다.

## 1. 목적

1. 회원가입/로그인 없이는 앱을 전혀 쓸 수 없게 한다 — "게스트로 계속하기"라는 무계정 경로를
   없애 온보딩을 단순화한다("손님입장" = 로그인, "회원가입" = 신규 가입, 둘 중 하나).
2. 회원가입 직후 연령대·성별·직업을 추가로 입력받아, AI 문진의 정확도를 높이는 데 활용한다.
   특히 직업 정보는 (예: 농업 종사자가 많은 사용자층 특성상) 증상 문진에 실질적으로 도움이 될
   수 있다고 보고 수집한다 — 통계/관리 목적이 아니라 AI 프롬프트 입력값이 1차 목적이다.
3. 앱 이름을 더 친근한 "홈 닥터"로 바꾼다.

## 2. 범위 결정 사항 (브레인스토밍에서 확정)

- **게스트 모드**: 완전 제거. `app/guest/page.tsx`, `InterviewApp`의 `mode: 'guest'` 분기,
  `WelcomeScreen`의 "게스트로 계속하기" 버튼을 모두 삭제한다. `getViewer()`가 반환하는
  `role: 'guest'`(= Clerk 세션 없음)는 개념적으로 남지만, 그 결과로는 여전히 `WelcomeScreen`만
  보여준다 — 로그인/회원가입을 유도하는 용도로만 쓰인다.
- **"손님입장" 명칭**: 기존 회원의 로그인 진입점을 가리키는 사용자 대상 표현이다(대상 사용자층에
  익숙한 표현 사용). 기능적으로는 `/sign-in`(Clerk 이메일+비밀번호 로그인)으로 이동하는 링크다.
  인증 식별자 자체(이메일+비밀번호)는 2026-09-11 문서에서 바뀌지 않는다 — Clerk의 전화번호 로그인은
  여전히 유료 플랜 전용이라 사용하지 않는다.
- **API 라우트 보호 범위 확장**: 게스트 제거에 따라 `/api/triage`, `/api/specialists`,
  `/api/interview`, `/api/synthesize`, `/api/transcribe`를 익명으로 호출할 이유가 없어진다.
  `proxy.ts`의 보호 라우트 목록에 이 다섯 개를 추가해 비로그인 호출을 차단한다(기존에는 게스트
  지원을 위해 의도적으로 열어뒀던 것).
- **기본정보 저장 위치**: 새 DB 테이블을 만들지 않는다. 기존 전화번호와 동일하게 Clerk 사용자의
  `unsafeMetadata`에 저장한다: `{ phoneNumber, ageBand, gender, occupation }`. 이유는 2026-09-11
  문서의 전화번호 저장 방식과 동일 — Clerk가 이미 회원정보의 단일 진실 공급원이고, 이 필드들은
  검증이 필요 없는 일반 프로필 값이다.
- **연령대 구간**: 5세 단위, 다음 18개 고정 목록(드롭다운)으로 확정한다.
  `10세 미만, 10~14세, 15~19세, 20~24세, 25~29세, 30~34세, 35~39세, 40~44세, 45~49세, 50~54세,
  55~59세, 60~64세, 65~69세, 70~74세, 75~79세, 80~84세, 85~89세, 90세 이상`
- **성별**: `남성 / 여성 / 응답 안 함` 3개 중 선택.
- **직업**: 자유입력이 아닌 고정 드롭다운으로 확정한다(자유입력은 "농업"/"농사"/"농부" 등 표현이
  갈려 AI 프롬프트 활용과 추후 집계 모두에 불리함).
  `농업, 자영업, 회사원/직장인, 주부, 학생, 무직/은퇴, 기타`
- **필수 여부**: 전화번호와 동일하게 네 필드 모두 필수다. 하나라도 비어 있으면 `/complete-profile`로
  리다이렉트되어 앱의 나머지 기능(문진, 매니져 대시보드, 관리자 화면)에 진입할 수 없다 — 기존
  전화번호 단독 검사 로직을 네 필드 검사로 확장한다.
- **AI 프롬프트 반영 범위**: 트리아지(`runTriage`)와 전문의 1차 분석(`runSpecialistAnalysis`)에만
  환자 기본정보를 전달한다. 후속 문진 응답 처리(`runSpecialistFollowUp`)와 종합소견(`runSynthesis`)은
  이미 1차 분석 결과에 기본정보가 반영되어 있으므로 별도로 다시 전달하지 않는다(불필요한 토큰
  재전송 방지 — 기존 `runSpecialistFollowUp`의 설계 원칙과 동일).
- **기본정보 조회 방식**: 각 API 라우트가 클라이언트가 보낸 값을 신뢰하지 않고, 서버에서 Clerk
  세션(`currentUser()`)으로 직접 조회한다 — 2026-09-11 문서의 "클라이언트 claim 신뢰 금지" 보안
  원칙과 동일하게 적용한다.
- **앱 이름**: "다중 전문의 AI 문진" → "홈 닥터". 코드/실사용 문서(레이아웃 메타데이터, PWA
  매니페스트, 화면 문구, `README.md`, `CLAUDE.md` 프로젝트 개요)를 갱신한다. 날짜가 박힌 과거
  스펙/계획 문서(`2026-08-28-*`, `2026-09-11-*`) 본문은 그 시점의 기록이므로 수정하지 않는다.

## 3. 화면 흐름

```
"/"  (비로그인)
  └─ WelcomeScreen: "홈 닥터"
       [ 손님입장 ] → /sign-in  (이메일+비밀번호 로그인)
       [ 회원가입 ] → /sign-up  (이메일+비밀번호 가입)

로그인 성공 직후, unsafeMetadata에 phoneNumber/ageBand/gender/occupation 중
하나라도 없으면 → /complete-profile (전화번호+연령대+성별+직업 한 화면에서 입력)
  → 저장 성공 시 "/" 로 복귀 → 역할에 따라 문진 화면 / 매니져 대시보드 / 관리자 화면 분기
```

`app/guest/page.tsx`는 삭제하고, `/guest` 경로는 더 이상 존재하지 않는다.

## 4. 데이터 모델

새 테이블 없음. Clerk `unsafeMetadata` 확장:

| 필드 | 타입 | 설명 |
|---|---|---|
| `phoneNumber` | string | 기존 필드, 변경 없음 |
| `ageBand` | string | §2의 18개 구간 문자열 중 하나 (예: `"60~64세"`) |
| `gender` | `'male' \| 'female' \| 'unspecified'` | 화면 표시는 한국어, 저장값은 코드로 고정해 이후 로직에서 문자열 비교 오류를 방지 |
| `occupation` | string | §2의 7개 카테고리 문자열 중 하나 |

`medical_records` 테이블(2026-09-11 문서)은 변경하지 않는다 — 이 네 필드는 문진 시점의 AI 프롬프트
입력으로만 쓰이고, 문진 결과 자체(`interviewRecord` JSON)에 이미 근거로 녹아 들어가므로 별도 컬럼을
추가하지 않는다.

`CompleteProfileForm`이 `user.update({ unsafeMetadata: {...} })`를 호출할 때는 기존 `unsafeMetadata`를
덮어쓰지 않도록 항상 `{ ...user.unsafeMetadata, phoneNumber, ageBand, gender, occupation }` 형태로
병합해서 저장한다 (현재 코드는 필드가 하나뿐이라 문제가 없었지만, 필드가 늘어나는 시점부터는 병합이
필요하다).

## 5. AI 파이프라인 연동

`patientProfile` 타입을 새로 정의해 트리아지/전문의 분석 함수 시그니처에 추가한다.

```ts
type PatientProfile = { ageBand: string; gender: string; occupation: string };
```

- `runTriage(transcript: string)` → `runTriage(transcript: string, profile: PatientProfile)`
  프롬프트 앞부분에 "환자 기본정보: 연령대 {ageBand}, 성별 {gender}, 직업 {occupation}" 한 줄을 추가한다.
- `runSpecialistAnalysis(specialtyId, transcript)` → 동일한 `profile` 매개변수를 추가해 동일한 형식의
  한 줄을 프롬프트에 포함한다.
- `runSpecialistFollowUp`, `runSynthesis`는 변경하지 않는다(§2 근거 참고).
- `app/api/triage/route.ts`, `app/api/specialists/route.ts`가 각각 `currentUser()`로 Clerk 사용자를
  조회해 `unsafeMetadata`에서 `PatientProfile`을 구성한 뒤 위 함수들에 전달한다. 필드가 없는 경우(이론상
  `/complete-profile`을 거치지 않고는 도달할 수 없지만 방어적으로) 빈 문자열로 대체하고 프롬프트 줄
  자체를 생략한다.

## 6. 보안

- §2의 "API 라우트 보호 범위 확장"에 따라 `proxy.ts`의 보호 라우트 목록에 `/api/triage`,
  `/api/specialists`, `/api/interview`, `/api/synthesize`, `/api/transcribe`를 추가한다.
- `PatientProfile`은 클라이언트 요청 바디로 받지 않고 서버가 Clerk 세션에서 직접 조회한다 —
  사용자가 다른 연령대/직업을 사칭해 AI 프롬프트를 조작할 수 없도록 한다.
- 그 외 인증/저장 관련 보안 원칙은 2026-09-11 문서를 그대로 따른다(변경 없음).

## 7. 에러 처리

- `CompleteProfileForm` 저장 실패 시(네트워크 오류 등) 기존과 동일하게 화면에 에러 메시지를 보여주고
  재시도할 수 있게 한다. 네 필드 중 하나라도 비어 있으면 클라이언트 단에서 제출을 막는다(각 입력이
  모두 `required`).
- `unsafeMetadata` 병합 저장 시 기존 값을 덮어쓰지 않도록 §4의 병합 방식을 반드시 지킨다.

## 8. 테스트

- Vitest 단위 테스트: `runTriage`/`runSpecialistAnalysis`가 `PatientProfile`을 프롬프트에 포함하는지
  (프롬프트 문자열 검증), `proxy.ts`의 보호 라우트 매처가 다섯 개 API를 포함하는지.
- 수동 검증: 회원가입 → 기본정보(전화번호/연령대/성별/직업) 입력 → 문진 진행 → 저장 확인. 정보 미입력
  상태로 `/`나 문진 API에 직접 접근 시 `/complete-profile`로 리다이렉트(페이지) 또는 401/403(API)
  응답 확인. `/guest` 경로가 404인지 확인.

## 9. 이번 스펙에 포함하지 않는 것

- 게스트 → 회원 전환 플로우(2026-09-11 문서와 동일하게 범위 밖 — 애초에 게스트 자체가 사라짐).
- 연령대/성별/직업을 이용한 통계·집계 대시보드. 이번 스펙은 AI 프롬프트 입력 용도로만 수집한다.
- 전화번호 기반 로그인(Clerk 유료 플랜 필요) — 이메일+비밀번호 로그인 유지.
